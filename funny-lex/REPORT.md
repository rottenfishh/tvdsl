# Отчёт по домашним заданиям: язык Funny (HW1–HW4)

Все задания — одна программа, каждое следующее строится на предыдущем:

```
текст ──► лексер (HW1 + P02) ──► парсер (HW2) ──► AST ──► семантический анализ (HW3) ──► аннотированный AST + ошибки
          lexgen.py                funny_parser.py         funny_semantic.py
          funny_lexer.py           funny_ast.py            funny_types.py, funny_symbols.py

аннотированный AST ──► IR (HW4) ──► CFG + живость ──► оптимизации ──► граф конфликтов + раскраска ──► (проект: JVM)
                       funny_irgen.py  funny_cfg.py     funny_opt.py     funny_regalloc.py
                       funny_ir.py                      funny_irinterp.py — проверка «до = после»
```

Язык реализации — Python 3.8+, без сторонних библиотек. Все тесты: `python lexgen.py` (HW1) и
`python run_tests.py` (HW2–HW4). Подробные объяснения кода — `HW2_EXPLAINED.md`, `HW3_EXPLAINED.md`, `HW4_EXPLAINED.md`.

## 1.3. Ловушка

- Состояние 0 — ловушка: ничего не принимает, все переходы из него ведут в него же.
- Таблица полная: для каждого состояния и каждого из 256 байтов задан переход; любой переход,
  которого нет в регулярках, ведёт в ловушку.
- Символы вне алфавита (байты 128..255) ведут в ловушку из любого состояния, кроме тела комментария `//`.
- `lex()` в `lexgen.py`: если с текущей позиции не начинается ни один токен, он выдаёт `ERROR` и пропускает один байт.

## 1.4. Тесты

- Все обязательные сценарии HW1: пустая строка; пробелы/табы/CRLF; `0`, `00`, `01`; идентификаторы с `_`;

- Покрытие алфавита: каждый из 256 байтов проверяется отдельно по правилу `expected_single_char`.

# HW2. Парсер: LL(1), рекурсивный спуск

## 2.1. Что сделано

| Часть | Файл | Суть |
|---|---|---|
| Лексер с позициями (P02) | `funny_lexer.py` | читает таблицу ДКА из HW1, режет текст по правилу «самый длинный кусок», у каждого токена строка и столбец (в символах, не в байтах); ошибки — отдельным списком |
| Парсер | `funny_parser.py` | ветка LL(1): одна функция `parse_*` на правило грамматики, выбор правила по одному текущему токену |
| AST | `funny_ast.py` | узлы-dataclass'ы с позицией; печать деревом (`dump`) и в JSON (`to_json`) |
| Обработка ошибок | `funny_parser.py` | режим паники: ошибка ловится в цикле операторов блока или определений модуля, токены пропускаются до синхронизирующего |
| Командная строка | `funny.py` | `--parse-only` — дерево HW2, `--json`, `--tokens` |
| Грамматика | `grammar.txt` | финальная EBNF, приоритеты, FIRST/FOLLOW, преобразования, отклонения |

## 2.2. Грамматика и приведение к LL(1)

Полностью — `grammar.txt`. Главные преобразования:

1. **Выражения, условия и предикаты — одна грамматика.** По `(` нельзя выбрать между арифметикой и условием
   (`if ((a+b) > c)` и `if ((a > b) and c)`) — конфликт FIRST, не решаемый никаким конечным k.
   Разница `int` / логическое значение проверяется в HW3.
2. **Устранение левой рекурсии:** `sum = sum "+" term | term` → `sum = term { "+" term }` (цикл `while`).
3. **Левая факторизация:** функция и формула (общее `имя ( параметры )`, выбор по `=>`), три вида присваивания
   (общее имя, выбор по `=` / `[` / `,`), переменная / вызов / элемент массива.
4. **Висячий else** — единственный конфликт LL(1), решён жадно: `else` относится к ближайшему `if`.

Приоритеты (от слабого к сильному): `->` (правая ассоциативность) < `or` < `and` < `not` <
сравнения (не ассоциативны) < `+ -` < `* /` < унарный `-` < первичные выражения.

## 2.3. AST и обессахаривание

Узлы: `Module`, `Function`, `Formula`, `VarDef`; операторы `Assign`, `If`, `While`, `Block`, `Assert`, `Assume`;
выражения `Num`, `Bool`, `Var`, `Unary`, `Binary`, `Call`, `Index`, `ArrayUpdate`, `Quantifier`. Формат — `AST.md`.

Сахар `a[i] = v;` раскрывается парсером сразу в функциональное копирование
`Assign(["a"], ArrayUpdate("a", i, v))` (в `funny.ru.md`: `a = set(a, i, v)`).

## 2.4. Обработка ошибок

- Каждое сообщение — `строка:столбец: текст`, например `2:15: ожидалась ')' после условия, а встретилось '{'`;
  `funny.py` печатает под ним строку исходника и `^`. Забытая `;` в конце строки показывается сразу после
  предыдущего токена.
- Синхронизирующие токены в блоке: `;` (съедается), `{ } if while assert assume EOF`; на верхнем уровне —
  пропуск до тела функции `{` (тело всё равно разбирается) или до `;` формулы.
- Зацикливание невозможно: каждая итерация цикла восстановления продвигается хотя бы на один токен.
- Лексические ошибки (`01`, `@`, не-ASCII) не останавливают разбор: `01` дальше идёт как число.

## 2.5. Отклонения от `funny.ru.md`

Полный список с причинами — `grammar.txt`, раздел 7. Главные: необязательное слово `function`;
необязательная `;` после формулы; один индекс у массива (`a[i]`, но не `a[i][j]` — двумерных массивов в Funny нет);
пустая программа — ошибка; `->` разрешено и в предикатах (так написан пример курса step12).

## 3.2. Таблицы символов (2 балла)

- Области: модуль (функции и формулы) → параметры → возвращаемые значения → локальные → переменная квантора.
  `requires` проверяется в области параметров, `ensures` — параметров и результатов, тело — во всех.
- Повторное объявление: если имя уже видно — ошибка с позицией первого объявления
  (два параметра `a`, параметр и результат, `uses` и параметр, переменная квантора, две функции, `x, x = f()`).
- Использование до объявления: тело обходится в порядке текста, локальная появляется на первом присваивании
  (или в `uses`); чтение раньше — «используется до первого присваивания».
- Функции и переменные — разные пространства имён; перепутать их — понятная ошибка.

## 3.3. Проверка типов (4 балла)

| Конструкция | Правило |
|---|---|
| `+ - * /`, унарный `-` | `int` → `int` |
| `== != < <= > >=` | `int`, `int` → `bool` |
| `not and or ->` | `bool` → `bool` |
| `a[i]` | `a : int[]`, `i : int` → `int` |
| `a[i] = v` (`ArrayUpdate`) | `a : int[]`, `i : int`, `v : int` → `int[]` |
| `length(a)` | 1 аргумент `int[]` → `int` |
| `f(...)` | число и типы аргументов = сигнатуре; 1 результат → его тип; несколько → только `x, y = f(...)` |
| формулы, `forall`/`exists` | только в предикатах; → `bool` |
| `if`, `while`, `invariant`, `assert`, `assume`, `requires`, `ensures` | условие типа `bool` |
| `x = e` | `e` не `bool`; `x` не параметр; тип `x` = тип `e` |

Параметры (в т.ч. массивы) только для чтения — это требование T1 проекта, проверяется уже здесь.
Полная таблица и решения по спорным местам — `TYPES.md`.

## 3.4. Вывод типов локальных (бонус)

Локальная без аннотации (`uses t` или просто `t = ...`) получает переменную типа `TypeVar`.
Первое присваивание унифицирует её с типом значения; дальнейшие использования проверяются против
выведенного типа. Конфликт (`x = 1; x = a;`) или невозможность вывода (`uses t` без присваиваний) — ошибка.
Итог записывается в `Function.locals`:

```
$ python funny.py tests/types_good/05_inference.funny --symbols
функция pick  @6:1
    параметры:    a: int[]
    возвращает:   r: int
    локальные:    t: int[], m: int, cnt: int, p: int, q: int
```

## 3.5. Диагностика (2 балла)

- Позиция узла + что ожидалось + что получено: `3:11: индекс массива: ожидался тип int, а здесь int[]`.
- Анализ не останавливается на первой ошибке. Каскады гасятся: выражение с ошибкой получает тип `error`
  (совместим со всем), неизвестное имя сообщается один раз на функцию, одинаковые сообщения не повторяются.

## 4.2. Оптимизации и их эффект

Проходы повторяются, пока код меняется. Обычно это 2–4 круга: свёртка открывает работу DCE, удаление меток склеивает блоки.

| Проход | Что делает | Пример (`tests/ir`) |
|---|---|---|
| `constprop` | в блоке помнит `x = константа`, подставляет, сворачивает `3 + 4`, `7 < 10`; `if true goto L` → `goto L`, `if false goto L` удаляется | `01_constants`: `b = a + 4` → `7`, ветка `else` пропадает |
| `algebra` | `x+0`, `x-0`, `x*1`, `x/1` → `x`; `x*0`, `x-x` → `0`; `x*-1` → `-x`; `x*2` → `x+x`; `x==x` → `true` | `01_constants`: `x * 1 + 0` → `x` |
| `copies` | `x := y` → дальше читаем `y`; `t := a + b; r := t` → `r := a + b` | все: убирает копии, которые генератор ставит после каждого выражения |
| `cse` | повтор `a + b`, `b + a`, `load v[i]`, `length a` в блоке → копия первого | `02_cse`: `(a+b)*(a+b)-(b+a)` — одно сложение |
| `dce` | удаляет `x := e`, если `x` мертва и `e` не может упасть | `03_dead_code`: `unused`, `k = x / 2` удалены; `x / y` и `a[x]` остались |
| `unreachable` | недостижимые блоки, `goto` на следующую строку, метки без переходов | `01_constants`: блок `x / 0` |

Чего оптимизации НЕ делают, потому что это изменило бы поведение программы:

* `x / x` не превращается в `1`, а `0 / x` не превращается в `0`: при `x == 0` должна быть ошибка;
* деление на переменную, `load`, `update` и `call` не удаляются, даже если результат не нужен: они могут упасть, а `call` может зациклиться.

## 4.3. Метрики

Все оптимизации включены. «Цветов» — число цветов в раскраске временных, то есть сколько ячеек нужно под временные.

| программа | функция | инструкций до → после | временных до → после | цветов до → после |
|---|---|---|---|---|
| 01_constants | calc | 20 → **2** | 10 → 0 | 1 → 0 |
| 02_cse | f | 7 → 4 | 5 → 2 | 2 → 2 |
| 02_cse | g | 9 → 5 | 7 → 3 | 2 → 2 |
| 03_dead_code | f | 12 → 4 | 6 → 0 | 1 → 0 |
| 04_overflow | f | 16 → **1** | 10 → 0 | 2 → 0 |
| 05_short_circuit | safe | 27 → 23 | 10 → 8 | 1 → 1 |
| 06_loops | gcd | 14 → 12 | 4 → 3 | 1 → 1 |
| 06_loops | sum_sq | 12 → 10 | 4 → 2 | 1 → 1 |
| 06_loops | bubble | 35 → 28 | 17 → 10 | 2 → 2 |
| 07_calls | divmod | 6 → 4 | 3 → 1 | 1 → 1 |
| 07_calls | fib | 12 → 11 | 6 → 5 | 2 → 2 |
| 07_calls | main | 8 → 5 | 5 → 2 | 2 → 1 |
| 08_registers | poly | 15 → 14 | 13 → 12 | 3 → 3 |

По всем 44 корректным программам (tests/ir, types_good, good, примеры курса):

* инструкций **601 → 429** (−29 %);
* временных **254 → 124** (−51 %).

Что видно из таблицы:

* **Константные программы сжимаются почти целиком.** В `04_overflow` 16 инструкций превращаются в одну `return -2147483648, -3, -2147483648, 0`: свёртка повторяет 32-битную арифметику JVM.
* **В циклах выигрыш меньше.** Оптимизации локальные, а значения живут между блоками. Например, в `bubble` есть `load b[j]` в двух разных блоках, и локальный CSE его не видит.
* **Число цветов маленькое (1–3).** Временные живут коротко, от записи до ближайшего чтения. Больше всего цветов там, где много промежуточных значений нужны одновременно: в `08_registers` это `(a+b)*(c+d) - …` — 3 цвета. С `--regs=2` три временные уходят в spill.

## 4.4. Проверка корректности

* **Группа 10.** 8 программ в `tests/ir`, в каждой ожидаемые результаты в `*.cases`, всего 44 входа. Среди них:
  * переполнение;
  * деление на 0;
  * выход за границы массива;
  * короткое замыкание;
  * рекурсия;
  * несколько результатов.

  IR до и после выполняется интерпретатором `funny_irinterp.py`. Оба результата равны ожидаемому, или оба — та же ошибка.
* **Группа 11.** 44 программы, случайные входы и 13 наборов оптимизаций; всего ≈ 6400 запусков, все совпали.
  Наборы такие: все оптимизации, каждая по одной, все без одной. Так проверяется, что каждый проход корректен сам по себе и не опирается на работу соседей.
* **Группа 12.**
  * Инструкций и временных после оптимизаций не больше, чем до.
  * Раскраска правильная: соседи разного цвета.
  * Отдельная проверка по живости: две одновременно живые переменные не получают один цвет.
  * `--O0` не меняет IR.

## 4.5. Ограничения

* **Оптимизации локальные**, как в задании. Константы и выражения не переходят через границы блоков.
  Глобальные версии (reaching definitions, available expressions, SSA из P07) — следующий шаг.
* **Живость — глобальная.** Без неё DCE не знал бы, нужна ли переменная после блока.
* **Раскраска жадная, она не оптимальна.** Узлы идут по убыванию степени, каждому достаётся наименьший свободный цвет. Копии `x := y` не дают ребра, но и не склеиваются (coalescing) явно.
* **Объявления остаются.** Переменные, ставшие ненужными (`unused` в `03_dead_code`), остаются в `locals`: в коде они больше не встречаются, кодогенератор может их пропустить.
* **Неинициализированные переменные.** Их чтение в Funny не определено. Интерпретатор даёт 0 / пустой массив, одинаково до и после оптимизаций.
